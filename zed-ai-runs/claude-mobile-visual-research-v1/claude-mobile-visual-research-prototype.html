    Method & harness conventions (not app evidence)
    • Evidence tag chips ("INFERRED" / "UNVERIFIED" …) are px-fixed annotations of the research layer: they intentionally do not scale with the studied UI's rem text-scale control, so they never distort the app layout being measured.
    • Contrast (computed on the documented tokens): ink #141413 on canvas #FAF9F5 = 17.50:1 (AAA) · error #B53333 on white = 5.72:1 (AA) · white on clay #D97757 = 3.12:1 — a UI-component pass only, so clay fills are kept to large controls (send button, bold icon) per the documented limitation.
    • Focus outlines (2px ink ring) are a QA-harness convention for keyboard operability — not an observed app style.
    • Text-scale control changes the document root font-size; the studied UI is authored entirely in rem so it scales, while the harness (px) does not. This scaling mechanism is a harness convention.
    • Keyboard simulation and safe-area stripes are QA overlays — never claimed to reproduce One UI behavior.
    • Frame geometry: outer aspect from official mm; inner viewport 320–430 CSS px at 2.167. Proportions only — no hardware pixels, DPR, or One UI safe areas.
    • Verbatim strings are quoted exactly as documented; nothing paraphrases inside quotation marks. Dummy content is intentionally generic.
    • Interaction inventory (documented behaviors only): send → numeric thinking timer → scripted dummy reply; capacity-error scenario + Retry (succeeds); drawer with Code entry; model sheet (models / Effort / Thinking "Extended"); attachment sheet → chips; Rename (stub) / Delete → persisting confirm; settings color mode; Code-mode sessions, mode dropdown with cloud vs remote option sets, new-session composer (queued toast), diff pane, persisting permission prompt. All other controls are labeled stubs.
    • Store-listing volatile facts (version/ratings/size) are intentionally absent.
