# الإجراء التنفيذي بعد اعتماد قرار الألوان

## القرار المثبت

- `#D97757`: هوية Micro والإنشاء وFAB فقط.
- `#C96442`: selected/current/pressed edge وunderline فقط.
- `#141413`: القيمة المالية، الالتزام الواضح، والخطر المبرر.
- الحفظ/التأكيد العادي: Warm Tint الحالي `#F5F4ED` مع نص `#141413` وأيقونة واضحة؛ عند الضغط يظهر edge `#C96442`.
- الاعتماد الكبير/الحذف النهائي: `#141413` ممتلئ مع نص أبيض، وكلمة ورمز وشرح للعاقبة.
- الألوان الدلالية: success/error/info/status للحالات والنتائج، مع كلمات وأشكال.
- `#964E33` و`#5F3120`: لا يدخلان هذه الموجة.
- لا Dark Mode، ولا palette جديدة، ولا تغيير في Brand Book أو أصول الشعار.

## الخطوة 1: تثبيت نقطة الانطلاق

قبل أي تعديل، يعيد المنفذ التحقق من حالة GitHub الفعلية، ويعمل على فرع تطوير مخصص لا على `main`. ينشئ جردًا للـ29 ملفًا وملفي metadata، ونسخة baseline كاملة، وrollback كاملًا، وSHA-256 وسجل حدود لكل ملف.

لا يُفترض أن فرع `micro-standard-v2-foundation-development` أو commit `f64e8616...` منشوران؛ يجب المقارنة مع حالة `main` الفعلية وقت بدء التنفيذ. لا يُعدّل Micro أو Accounting.

## الخطوة 2: تنفيذ الدلتا فقط

قبل التعديل، يقارن ZAI النسخة الحالية مع Waves 0–D السابقة ويحدد ما هو موجود فعلًا. لا يعيد تنفيذ تعديل موجود، ولا ينسخ من Prototype، ولا يطبق توصيات ZAI القديمة التي حُسم رفضها.

## الموجة A: العقود والتوكنز

تُحدّث العقود والـtokens التي تحتاجها فقط لتسجيل الفرق بين:

1. إنشاء/إضافة.
2. حفظ/تأكيد عادي.
3. اعتماد كبير/حذف نهائي.
4. نجاح/خطأ/انتظار/مراجعة.

يُسجل أن الحفظ العادي يستخدم Warm Tint وليس زرًا أسود ممتلئًا، وأن الضغط يستخدم edge `#C96442`، وأن نجاح الحفظ لا يعتمد على لون الزر وحده. لا تُضاف قيم لونية جديدة.

## الموجة B: Gallery وتركيب المكونات

تُحدّث أمثلة Gallery فقط لإظهار الأدوار الحقيقية:

- FAB/إنشاء بـ`#D97757`.
- حفظ عادي بـWarm Tint + نص داكن + أيقونة حفظ.
- ضغط الحفظ بـ`#C96442` edge.
- اعتماد كبير/حذف نهائي بـ`#141413` مع مسار تأكيد واضح.
- قيم مالية بـWarm-Ink دون أسطح سوداء إضافية.
- حالات success/error/pending/review بألوانها الدلالية مع كلمات وأشكال.
- Charts لا تصبح سوداء بالكامل ولا Terracotta بالكامل.
- Chips وsegments لا تستخدم تعبئة سوداء تلقائيًا إذا كان دورها selected/current؛ تستخدم الإشارة المعتمدة من Standard.

## الموجة C: التوثيق والتحقق

تُحدّث الملفات التوثيقية والـmanifest وverification فقط بعد نجاح A وB. يجب أن تذكر التقارير ما تغيّر فعلًا وما لم يتغير، وأن تفصل بين اختبار Gallery المحلي واختبار الجهاز الحقيقي.

## الاختبارات الإلزامية بعد كل موجة

- `git diff --check` وصحة JSON.
- فحص عدم إضافة ألوان خام أو أدوار غير مسماة.
- 320/360/390/430px.
- RTL واللغة العربية والأرقام الإنجليزية.
- 100/130/200%.
- focus وpressed وdisabled وloading وquiet completion.
- reduced motion وعدم وجود overflow أو تداخل FAB مع الأرقام.
- تباين الحدود والنصوص والأسطح.
- تحقق بصري من عدم ظهور أكثر من سطح أسود غير مبرر في viewport واحد.
- عدم ادعاء اختبار جهاز فعلي أو قارئ شاشة إذا لم يُنفذ.

بعد كل موجة يتوقف المنفذ ويكتب تقريرًا قصيرًا وحدود rollback. لا تُدمج الموجات أو تُرفع إلى `main` قبل مراجعة المالك.

## حدود لا يجوز كسرها

- لا تعديل Micro أو Accounting.
- لا منطق مالي أو formulas أو posting/reversal أو sync أو permissions.
- لا نقل جماعي أو إعادة تنظيم للمجلدات.
- لا Dark Mode.
- لا إدخال `#964E33` أو `#5F3120`.
- لا اعتماد Teal جديد؛ يبقى قرار link/action مستقلًا وغير داخل هذه الموجة.
- لا تحويل Terracotta إلى لون بيانات أو نجاح أو خسارة.
- لا نقل Prototype إلى Micro.
- إذا ظهرت حاجة إلى structural refactoring أو bulk file moves، يتوقف العمل ويبدأ أولًا Structure/Architecture/Code Organization Scan read-only، ثم مراجعة المالك قبل أي تنفيذ.

## بعد اكتمال Standard — Prototype HTML إلزامي

1. مراجعة المالك للحزمة النهائية.
2. إنشاء Prototype HTML تفاعلي مستقل داخل مجلد تسليم منفصل، وليس داخل `micro-standard-v2/`، ولا داخل Micro أو Accounting.
3. يجب أن يعرض Prototype كل تغيير بصري نفذ في Standard، لا عينة ناقصة فقط. الحد الأدنى هو: إنشاء/إضافة، حفظ/تأكيد عادي، ضغط الحفظ، اعتماد كبير، حذف نهائي، قيمة مالية، صف تشغيلي، selected/current، lifecycle states، success/error/pending/review، FAB، chart question-led، sheet/dialog، bottom navigation، overflow، وreduced motion.
4. يجب أن تكون المشاهد قابلة للتفاعل محليًا: تبديل الحالات، الضغط، loading، quiet completion، فتح وإغلاق sheet/dialog، وتغيير period أو state عند الحاجة. لا routes منتجية، ولا writes، ولا formulas، ولا data sources حقيقية.
5. يجب أن يعمل Prototype في RTL وبمقاسات 320/360/390/430px، مع 100/130/200%، وألا يعتمد على remote assets أو خدمة خارجية. يستخدم نفس tokens والعقود النهائية من Standard، ولا يضيف Palette أو theme.
6. يجب أن يحتوي المجلد على ملف HTML واضح، وملفات CSS/JS اللازمة، و`PROTOTYPE_README.md`، و`PROTOTYPE_COVERAGE.md` لربط كل مشهد بملف Standard والعقد الذي يمثله، و`PROTOTYPE_VALIDATION.md` لتسجيل ما اختُبر وما لم يُختبر.
7. يسلم ZAI ملف HTML قابلًا للتحميل ومجلدًا قابلًا للقراءة، إضافة إلى لقطات للمشاهد الرئيسية عند الإمكان. لا يُعلن Prototype منتجًا جاهزًا ولا مصدر حقيقة للـMicro.
8. تُسجل مشاكل التركيب في Prototype فقط أولًا، ولا يُعدّل Standard تلقائيًا بسببها. أي تعديل جديد على Standard يحتاج موجة وقرارًا مستقلًا.
9. بعد قبول Prototype، إعداد خطة مستقلة لنقل الأنماط إلى Micro.

## نقطة التوقف الحالية

الإجراء الصحيح الآن هو كتابة Prompt تنفيذ ZAI كاملًا بهذه الحدود. لا يبدأ ZAI تعديل الملفات قبل أن يقرأ هذا الإجراء ويثبت baseline وrollback.
