### J2 — Accrued expense → settlement without double counting

- **Zman: MISSING.** The `expense` table has no payable dimension (`finance/db.ts:108-171`); every expense writes cash-out. `receivable` is money owed **to** the shop only (`finance/db.ts:415`). An unpaid supplier bill cannot be represented without either distorting cash or omitting the expense.
- **Micro: ADAPTED (new capability).** `operating_expense_payable` = `[cash 0, payable +1, expense +1]`; `payable_settlement_cash` = `[cash -1, payable -1, expense 0]` — the settlement does **not** re-record the expense (delta table `policies.ts:276`); settlement requires an explicit `relatedEventId` and only that type may carry one (`policies.ts:339-341`); the editor lists settleable payables and links the source (`FinancialEventEditor.tsx:62-71`, `SettleablePayable` import `:31`). Corrections reverse both sides symmetrically (`policies.ts:413-415`).
- Data parity: the Zman→Micro meaning mapping for an unpaid bill is *lossy in reverse* — a Micro payable settled later would have to collapse into a single Zman expense row dated at settlement.

### J3 — Tracked material → purchase → explicit receiving → partial receiving → remaining quantity → correction

**Zman steps:** `SmartFinanceForm` purchase mode (`:70-89`) → `createPurchase` (`actions.ts:136`): validates linked component is tracked (`:210-213`, rejects otherwise), inserts `purchase` + `cash_movement out 'purchase'` (`:246-259`) **and** `catalog_movement in` in the same transaction (`:277-303`) with `unitCostCents=floor(total/qty)` and `totalValueCents=totalCents`. There is **no separate receiving step** — purchase *is* the receipt. Partial receiving is not modeled (full quantity lands at purchase date). Remaining quantity = live sum of active movements. Corrections: `updatePurchase:318` soft-deletes the old movement and inserts a new one; `adjustStock` (`inventory/actions.ts:431`) writes `manual_in`/`manual_out` (+ auto write-off expense when value>0, `db.ts:119-129`); `deletePurchase:561` cascades soft-deletes.

**Micro steps:** `SupplierPurchaseEditor` (`/suppliers/purchase/:id`, `MicroRouter.tsx:108-109`) → `supplierPurchaseService.recordPurchase` (`supplierPurchaseService.ts:101-137`) — cash/payable **only**, no inventory effect (truth string `:96`). Optional material link + `expectedQuantityMilli` (`:19-22`). Receiving = separate bridge: Suppliers page → `?purchase=<id>` opens `InventoryMovementEditor` type `receipt` (`InventoryMovementEditor.tsx:44-62`, contract `navigationContract.ts:55-56`); the editor prefills remaining quantity/value from `purchaseReceiptStatus` (`:157-181`) and shows «كمية مستلمة: X من Y» (`:533-534`). `receivePurchase` (`inventoryMaterialService.ts:731-785`) enforces: purchase material binding (`:756-768`), cumulative received value ≤ `totalMinor` (`:770-779`), cumulative received quantity ≤ `expectedQuantityMilli` while allowing intentional partial (`:780-785`), and idempotency by `operationKey`. Correction: `InventoryReversalEditor` (`/inventory/movement/:id/reverse`, `MicroRouter.tsx:126`) writes an opposite movement and never erases history (`InventoryReversalEditor.tsx:1-2,42-56`). Purchase edits are guarded so totals/expected quantity/link cannot drop below what was actually received (`supplierPurchaseService.ts:193-233`).

**Verdict: ADAPTED.** Step parity: Zman 4 steps (purchase+receipt merged) vs Micro 6 steps. Field mapping: `quantity` (integer) ↔ `expectedQuantityMilli` (milli, optional) + receipt `quantityDeltaMilli`; `unitCostMicroCents`/`totalCents`/`totalValueCents` ↔ `valueDeltaMinor` + `costKnowledge` (known/unknown) — **Zman's weighted-average per-unit cost is not preserved in Micro** (Micro stores only movement values and knowledge). Derived values: Zman COGS = weighted average at sale; Micro period COGS = `derivePeriodCogs` over consumption movements (`projectFinancialService.ts:575`). Correction parity: both non-destructive at the ledger level, but Zman's `updatePurchase` rewrites the movement row (soft delete + insert) whereas Micro appends a reversal — Micro's history is stronger. Offline/reload: Micro idempotent via operationKey; Zman via `idempotency_key` table (`orders/db.ts:129`).

### J6 — Order → preparation → delivery review → inventory consumption → collection/credit → settlement

**Zman:** status machine `draft|sent|confirmed|delivered|cancelled` (`orders/db.ts:96`); deposit recorded as `cash_movement 'deposit' in` at order create/update; delivery = `convertOrderToSale` (`actions.ts:1441`) — atomic transaction: sale row (full realized revenue `totalPrice+additionalProfit`, `:1525-1541`), deposit movement **reclassified** to `sale` (`:1549-1580`), **remainder cash-in inserted unconditionally** (`:1582-1601`), `deductForDelivery` inventory out (`inventory/actions.ts:196`, called `actions.ts:1604-1610`), status→delivered. Credit: no order-level credit — the remainder is booked as cash even if uncollected (cash-basis P&L). Unique index prevents double conversion (`finance/db.ts:201-203`); `reverseSale:1650` undoes everything (soft deletes) and restores status `confirmed`.

**Micro:** status machine `draft|provisional_agreement|confirmed|in_progress|ready|delivered|settled|postponed|cancelled|needs_review` (`craft-order/types.ts:74-84`) + orthogonal `SettlementStatus` incl. `debt`/`cancelled_*` (`:86-95`); preparation via `markReady`/`resumeAfterReview` (`fulfillmentService.ts:59-123`); delivery review surface `/orders/:id/deliver` (`MicroRouter.tsx:100`) → `deliveryReviewService.buildReview:155` (consumption proposal) → `commitDelivery:308` writes `delivery_consumed` event + consumption movements linked to the delivery event (D2 contract); plain `fulfillmentService.deliver:124-161` (ready→delivered, re-delivery gets a fresh idempotency key `:137-141`); consumption = explicit inventory movements (never automatic); collection: `collectFullRemaining:163-184`, `collectDebt:187-215` (partial, later), `collectFromSheet:210-238` via the unified Collect sheet (`collectionService.ts:150-233`, which also does wallet attribution + honest degradation on attribution failure `:220-227`); credit modeled as `receivableMinor` + `settlementStatus='debt'`; `reverseCollection:239` documented; `registerRemainingDebt:288`; settlement → status `settled`.

**Verdict: PARTIAL/ADAPTED.**
- **Data-meaning difference (P1):** Zman books the uncollected remainder as cash-in at delivery (`actions.ts:1582-1601`), Micro tracks it as receivable. Period readings of the two apps differ for credit sales; any migration must map Zman's `cash_movement 'sale'` remainder into Micro collection events.
- **Back-dating limitation (P2):** Micro order collections and their wallet allocations are stamped with the recording date (`fulfillmentService.ts` uses `this.now()`; `distributeUnallocated` defaults `occurredOn: ammanDate(this.now())` `projectFinancialService.ts:989`; Collect sheet has no date input), while Zman lets the owner set `depositDate`/sale dates. A collection recorded a day late lands in the wrong statement period with no repair path short of reversing and re-collecting the same day.
- Correction/reversal parity: MATCHED (J9). Offline: MATCHED (Micro fully offline; Zman server-bound). Exit: Micro `?from` on all order surfaces; Zman page navigation.

### J7 — Direct sale with and without inventory consumption

- **Zman:** manual sale via `SaleForm` → `createSale:1069` (`source='manual'`); INV-4 deposit-netting — a manual sale attached to an order posts only `amount − order.depositCents` to cash to avoid double-counting the deposit (`actions.ts:1124-1130`, update path `:1270`); manual sales never touch inventory (deduction only happens for order sales).
- **Micro:** `DirectSaleEditor` (`/direct-sales/new|:id`, `MicroRouter.tsx:94-95`) → `directSaleService.record:73-123` — fields `revenueMinor, collectedMinor, collectionStatus, catalogItemId, costMinor (optional/unknown), occurredOn, note, quantity`, price-cut revision (`:100-107`), revision-count conflict guard on update (`:125-167`); inventory consumption is an **explicit optional post-save bridge** `/inventory/movement/consume?sale=<id>` (`DirectSaleEditor.tsx:507`); the consume service validates the sale is active (cancelled sales are not consumable, `inventoryMaterialService.ts:810-830`).
- **Cancel (FT-02 verified):** `cancel:168-220` writes a documented cancel revision, then `reverseAllocationsForCancelledSale:225-271` writes deterministic mirror `reversal` CashContinuityEntries keyed `sale-cancel:{saleId}:{allocationId}` for every active allocation linked by `sourceRefKind='sale'`; idempotent (repeated cancel reuses; already-reversed ids skipped `:237-247`); honest degradation on mirror failure surfaces as `allocationReversalNotice` without hiding the cancel (`:220`). Deposit refunds are never wallet-attributed so no mirror is needed (commit note verified against code: allocations only carry `sourceRefKind 'sale'`).
- **Verdict: ADAPTED.** INV-4 netting is Zman-only because Micro manual sales are order-independent; a Zman manual sale tied to an order maps ambiguously to Micro (direct sale vs order collection) — flagged P2.

## Field-Level Parity Notes

1. **Money minor units differ by 10×** — Zman: 1 JOD = 1000 fils, stored as integer fils, with micro-cents (fils×1000) precision for unit costs (`lib/money.ts:1-2`, `finance/db.ts:31-42`); Micro: `MoneyMinor` formatted `minor/100` (2-decimal JOD, `presentation/formatters.ts:56-58`). Every cross-system field mapping must apply ×10 (fils→Micro-minor) or /10 — silent divergence would be a 10× money error. No code path currently crosses the two systems (P2-1, latent).
2. **Quantity precision** — Zman `quantity` integer (`purchase_quantity_positive` check `finance/db.ts:81`); Micro `quantityMilli` (fractional to 1/1000). Zman history migrating to Micro would need ×1000; reverse is lossless only for integers.
3. **Cost basis** — Zman stores per-movement `unitCostCents` (weighted average at sale) and `totalValueCents` (exact); Micro stores only `valueDeltaMinor` + `costKnowledge:'known'|'unknown'` and derives period COGS. Zman's weighted-average unit cost is not reconstructible in Micro without re-derivation.
4. **Dates** — Zman rows carry user-settable business dates (`date`, `depositDate`, `receivedDate`); Micro general events carry `occurredOn` (user date) but **order events/collections carry only `createdAt`** (recording time) — see J6/P2-7.
5. **Soft delete vs append-only** — every Zman table has `deletedAt` (in-place mutation allowed); Micro records are never deleted — corrections are reversal/revisions appended with reasons and links. Meaning preserved but migration must convert Zman soft-deleted rows into Micro reversal records (or drop them) — currently no converter exists (P1-1).
6. **categoryLabel end-to-end trace (verified):** editor input (optional, `maxLength=80`, suggestion chips) `FinancialEventEditor.tsx:819-837` → normalization in editor `:350,808` → domain freeze `normalizeCategoryLabel` (`policies.ts:145-151`, only on `operating_expense_*`, `:344-347`) → stored with the event in `financial-events` (`IndexedDbLocalStore.ts:1256-1258`; export includes it via `readSnapshot`) → read models: statement grouping incl. unclassified fallback and per-line `?event=` links (`statementService.ts:503-534`), suggestions (recent-first, reversals skipped, `expenseCategorySuggestions.ts:33-44`), period reader buckets by relationship/purpose (`projectFinancialService.ts:587-598`). Correction of a label = documented reversal + new event (domain comment `types.ts:58-61`). No drift found between preview, save, and read.
7. **Schema/export versions (verified):** `localSchemaVersion = 35` (`types.ts:37`), `localExportVersion = 27` (`types.ts:44`) — the "v27" claim is the *envelope* version; the storage schema is v35. Import accepts the migration chain back to legacy v6/14 and rejects unknown versions (`localTransferService.ts:2485-2520`).

- **P2-5 — Zman backup partial scope (Zman-side).** `BackupModal` omits expenses/purchases/sales/cash movements/receivables and has no digest or restore (`BackupModal.tsx:31-71`) — a false sense of backup for a Zman user. Micro envelope v27 is the reference model.
- **P2-6 — Wallet archival missing.** Zman `account.isArchived` + `archiveAccount` (`finance/db.ts:269`, `actions.ts:2848`); Micro `CashWallet` has no archive/retire field (`domain/cash-continuity/types.ts:12-20`, no archive code in `pages/CashWallets.tsx`).
- **P2-7 — Collections cannot be back-dated (J6).** Micro order collections and their wallet allocations stamp the recording date (`fulfillmentService.ts` now-based events; `distributeUnallocated` defaults `occurredOn: ammanDate(this.now())` `projectFinancialService.ts:989`; Collect sheet has no date field), while Zman allows `depositDate`/sale-date edits. Late-recorded collections land in the wrong statement period with no repair except same-day reversal+re-collect.

**P3 (enhancements):**
- **P3-1 — `categoryLabel` max 80** (`FinancialEventEditor.tsx:826`, `policies.ts:145`) vs Zman category 200 (`finance/db.ts:143-144`) — truncation on input, not a validation error.
- **P3-2 — Statement category grouping is raw-label, case-sensitive** (`statementService.ts:508`) vs Zman's case-insensitive catalog dedupe (`actions.ts:2652-2658`) — mixed-case duplicates split groups (rare in Arabic).
- **P3-3 — Purchase-edit expected-quantity guard skipped when cleared to null** (`supplierPurchaseService.ts:222`) — clearing `expectedQuantityMilli` bypasses the received-quantity check (value check still applies; domain revalidation partially compensates).
- **P3-4 — Schedule completion idempotency uses the first delivered event** (`scheduleService.ts:206-208`) — inconsistent with the FT-01 "last effective delivery" reader convention; currently harmless because completion is monotonic.

## Conclusion

The 17 journeys are faithfully transferred in direction and financial semantics: 5 exact matches, 11 adaptations that are supersets of Zman behavior, 1 partial (J6, due to the credit-sale model difference and collection dating), and one Zman-side miss (J2 accrued expenses, which Micro newly covers). Micro's data model is a deliberate re-architecture (event-sourced, append-only, offline-first) rather than a port: the Zman tables map onto 20 of Micro's 32 stores with meaning preserved, with `message_template` and `snippet` dropped and several concepts split or derived. No P0 defects remain on Micro main @ `1242aa6`; the open parity risks are concentrated in cross-system conversion semantics (money units, cost basis, credit sales, date semantics) that only matter if a data bridge or comparative reporting is ever built.
